# tokens

DTCG design tokens → CSS, WordPress `theme.json`, `DESIGN.md`, and more, as one binary.

```sh
mise use github:kickinrad/tokens
tokens          # build every target in tokens.config.mjs
tokens --check  # fail if a committed output is stale
```

```js
// tokens.config.mjs
export default {
  targets: ["css", "theme-json", "design-md"],
  media: { "(max-width: 850px)": ["tokens/responsive.tokens.json"] },
  include: ["builtin:material", "vendor/*.tokens.json"], // optional silent base layers; tokens/ overrides them
  kit: { name: "acme", root: "design" }, // optional; targets also get ctx.root (absolute), ctx.version (from ./VERSION), ctx.name
  css: { path: "src/styles/tokens.css", layer: "base", prelude: "" },
};
```

`kit` is optional. When set, `name` is required, `root` is the kit folder relative to the config and defaults to `design`, and `VERSION` in the working directory must hold a semantic version. Every target's `ctx` then also carries `root`, `version` and `name`; without `kit` it carries none of them.

With a kit, every generated text file (`.css`, `.scss`, `.js`, `.mjs`, `.ts`, `.kt`, `.kts`, `.swift`, `.yaml`, `.yml`, `.toml`, `.sh`, `.py`, `.conf`, `.md`, `.html`, `.svg`, `.xml`) starts with a header naming the engine, the kit and the target, and saying not to edit it; it sits after any front matter, doctype, xml declaration, shebang or `@charset`, and within the first 10 lines. `.json` and other extensions get none. `tokens --check` fails a kit output none of whose first 10 lines matches `/^\W*Generated by \S+.*\bdo not edit\b/i` (one line: comment marks, "Generated by <name>", then "do not edit"), naming the path. The systems guard reads the same rule.

A kit may declare `contrast: [{ fg, bg, min }]` (token paths and a minimum ratio: 4.5 for text, 3 for marks). Every pair is resolved in the base tokens and in each `media` set, and a pair under its floor, or a path that is not a colour token, fails the build and `--check`, naming the pair, the mode, the ratio and the floor.
The colour maths (`luminance`, `contrast`, `mix`, `bestOn`, `stateLayer`, `textSafe`, `hsl`, `rgb`) live in `src/color.mjs`.

With a `kit`, `tokens --check` also validates the token sources (`tokens/*.tokens.json`, media files and `include` globs) against the official [DTCG 2025.10 format schema](https://www.designtokens.org/schemas/2025.10/format.json), vendored under `src/schema/2025.10/` (re-fetch with `node scripts/fetch-dtcg-schema.mjs`). Each error names the file and the path, e.g. `tokens/brand.tokens.json: $.color.ink.$value must be object`; a hex-string colour fails because 2025.10 colours are objects.

## Built-in Material 3 baseline

`include` entries are file globs, or the name of a layer the binary carries. `"builtin:material"` is Google's Material 3 token set (`md.ref`, `md.sys` and `md.comp`, plus the tv-material card defaults), so a kit starts from Material and writes only what it changes. Built-in layers sit beneath file includes, which sit beneath the project's `tokens/` and its `media` files. A config without a `builtin:` entry builds exactly as before; an unknown name fails with `Unknown built-in include`.

The data is `material/`, generated by `scripts/vendor-m3.mjs` from the Compose Material 3 token files in [androidx/androidx](https://github.com/androidx/androidx) (Apache-2.0, The Android Open Source Project) at the SHA in `material/manifest.json`. `material/index.mjs` imports every file as JSON, so `bun build --compile` embeds the data and the binary needs no `material/` beside it. Never edit `material/` by hand; CI runs `bun scripts/vendor-m3.mjs --check`.

To re-vendor, run `bun scripts/vendor-m3.mjs --sha <androidx sha>` on a branch, review the diff, run `bun test` and open a PR. CI checks `material/` against the recorded SHA. A new Kotlin form the script does not know fails loudly, naming file and line.

## A kit's `theme.toml`

With a `kit`, a hand-written `<kit root>/theme.toml` holds the kit's palette per mode (plain `#rrggbb` hex), which palette colour fills each Material colour role, and its faces:

```toml
name = "acme"                          # must equal kit.name in the config
default = "night"                      # the base mode
[media]
day = "(prefers-color-scheme: light)"  # every other mode and its media query
[palette.night]
ink = "#101418"
blue = "#7aa2f7"
[palette.day]
ink = "#f6f6f6"
blue = "#2e7de9"
[roles]
"md.sys.color.surface" = "ink"         # a token path to a palette colour, resolved per mode
"md.sys.color.primary" = "blue"
[faces]                                # brand, plain, mono, icon
brand = "Some Sans"
mono = "Some Mono"
```

`tokens` turns it into DTCG 2025.10 files (colours as `{ colorSpace, components, hex }` objects) beside the kit's other tokens: `<root>/tokens/theme.tokens.json` for the default mode (the palette under `<name>.palette.<colour>`, the faces under `<name>.font.<face>`, every role at its path) and `<root>/tokens/theme.<mode>.tokens.json` for each other mode (every role, in that mode's colour). They are build outputs, never hand-edited: `tokens --check` byte-compares and schema-checks them. The default file is an include layer above `include` and below the project's `tokens/`; each mode file joins the `media` set for its query. A role naming a colour a mode's palette lacks fails the build, naming the role, the colour and the mode. A kit with no `theme.toml` builds as before.

## The `derived` target

`"derived"` computes the Material colour roles a palette has no step for (the on-colours, the accent containers, the fixed roles, and a mark per item of a group) and writes them as token files, one for the base mode and one for the Day media. The Day file belongs in `media`; `tokens --check` keeps both current. A config without it builds as before. Every fact about the kit is an option:

```js
derived: {
  prefix: "acme",                      // the kit's token prefix; ctx.name when a kit is declared
  accents: ["primary", "amber"],       // roles that get an on-colour and a container
  custom: ["amber"],                   // roles with no Material path: they sit under <prefix>.color
  fixed: ["primary"],                  // accents that also get -fixed roles (optional)
  blend: "acme.color.container-opacity", // the container's state-layer fraction (a token path)
  marks: { group: "track", darkerInDay: ["slow"] }, // optional: <prefix>.<group>.<item>.color gets a mark role
  dayFiles: ["tokens/day.tokens.json"], // the Day media files to read
  out: { night: "tokens/derived.tokens.json", day: "tokens/derived-day.tokens.json" },
}
```

A missing required option fails, naming it. The colour roles read are Material's: `surface`, `surface-container-lowest`, `surface-container-low`, `on-surface`, `inverse-surface`, `inverse-on-surface` and the accents. `src/motion.mjs` (springs as CSS `linear()` easings) and `src/type.mjs` (the fifteen type styles) are libraries for other outputs, not targets.
